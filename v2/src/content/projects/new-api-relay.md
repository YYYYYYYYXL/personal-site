## 项目背景

不同上游模型服务的接入方式、模型名称和使用记录需要统一管理。我基于开源 **New API** 部署自托管的大模型 API 中转服务，将模型渠道、用户 API Key、调用额度与使用记录集中到同一平台。

**这是对第三方开源项目的部署与配置实践，我不是 New API 的原作者，本站也不代表上游模型服务商的官方服务。** 项目展示聚焦我实际参与的部署、配置和运维工作，不将上游产品功能视为个人原创开发成果。

## 我实际负责的工作

- 在 Ubuntu 环境使用 Docker Compose 组织 New API、PostgreSQL 和 Redis。
- 配置 Nginx 反向代理及 HTTPS，让应用通过域名入口访问。
- 配置上游模型渠道、模型映射、价格与用户分组，并进行过调用验证。
- 操作用户、API Key 和平台额度管理，查看调用与额度变化记录。
- 建立数据库定期备份、SHA256 校验和异机副本保存流程。
- 将备份恢复到独立测试数据库，验证恢复过程并核对关键业务表行数。

## 技术实现

### 服务组成与请求链路

```text
API 客户端
    ↓ HTTPS
Nginx
    ↓
New API
    ├── PostgreSQL：业务数据持久化
    ├── Redis：缓存及运行辅助
    ↓
已配置的上游模型 API
```

Nginx 提供 TLS 与反向代理入口；New API 承担用户认证、模型路由、额度管理和调用记录；PostgreSQL 保存业务数据；Redis 提供缓存及辅助能力。Docker Compose 管理这些服务的运行关系。

上游密钥由服务端受控管理，下游用户使用平台生成的 API Key。数据库和缓存通过容器内部网络通信，不作为公开网站入口。

### 渠道与额度管理

渠道、模型映射和分组决定请求可以访问哪些上游服务。平台根据已配置的模型价格及实际调用量扣减用户额度。

平台内部调用额度与上游服务商账户余额属于两套独立账务。平台额度充足不代表上游渠道一定可用；实际调用仍取决于渠道授权、余额、限流和服务状态。本文不公布上游凭据、用户信息或实际计费明细。

### 备份与恢复验证

定期生成 PostgreSQL 逻辑备份，并以 SHA256 检查文件在保存或传输后是否变化；同时将备份副本保存在服务器以外的位置。

恢复验证使用独立测试数据库，避免覆盖生产数据。校验和只能证明文件是否发生变化，不能替代数据库恢复演练。

## 已有成果

- 完成 New API、PostgreSQL、Redis 的容器化部署及 Nginx、HTTPS 配置。
- 已配置模型渠道并进行调用验证，实际操作过用户、API Key、分组、价格与额度管理。

- 根据项目记录，完成过一次恢复演练，恢复 **38 张数据表**，并核对部分关键业务表行数。这是一次演练记录，不代表对所有故障场景的恢复保证。

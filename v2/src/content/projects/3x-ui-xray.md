## 项目背景

这项实践基于第三方开源 3X-UI 管理面板与 Xray-core，围绕 Ubuntu 环境中的原生服务部署、管理入口保护、节点配置和客户端管理展开。

**我不是上游软件的原作者。** 项目重点是部署、配置与运维方法，不将面板或核心本身的功能描述为个人原创开发成果。公开介绍省略真实服务入口和全部节点连接参数。

## 我实际负责的工作

- 采用原生 systemd 方式组织 3X-UI 和 Xray 服务，区分服务启动、进程和监听状态；此方案不使用 Docker。
- 整理 Nginx 反向代理与 HTTPS 管理入口配置，让管理服务与外部访问入口承担不同职责。
- 梳理 VLESS、REALITY 与客户端配置的关系，区分管理面板访问和实际数据传输。
- 整理按使用者或设备分配独立客户端标识、额度、有效期和停用权限的流程。
- 整理 Windows 与平板客户端的配置、导入和连通性检查方法。
- 记录面板访问异常、连接超时、握手失败和流量变化的排查步骤，以及数据库备份和升级前检查事项。

## 技术实现

### 原生服务管理

服务由 systemd 管理。3X-UI 提供管理功能，Xray-core 承担实际连接处理；二者的职责与访问入口需要分开理解。

排查时先确认服务和进程状态，再检查监听、应用日志和网络规则，避免把管理面板的可访问性误认为客户端连接已经通过验证。

### 管理平面与数据平面

```text
管理平面：管理员浏览器 → HTTPS 入口 → 管理服务

数据平面：授权客户端 → 数据处理核心 → 目标服务
```

Nginx 和证书用于管理入口的 HTTPS 访问。数据链路由对应客户端和 Xray 核心处理，不能把管理入口的反向代理链路直接套用为节点数据链路。

公开页面仅展示这一职责划分，不展示真实域名、IP、监听端口、随机管理路径、具体目标站点、路由规则或可导入的节点配置。

### 客户端管理与验证

按使用者或设备分配独立客户端，便于分别记录流量、设置使用期限并在需要时停用。客户端分享材料包含连接凭据，应按敏感数据管理，不能作为项目截图或附件公开。

文档将服务状态、监听状态、客户端配置、网络连通性和流量记录分别列为检查维度。客户端与云平台的流量统计口径可能不同，应核对各自定义，而不是假设两者数值完全一致。

### 运维与数据保护

维护流程覆盖服务日志、配置检查、数据库备份及升级前后的状态核对。管理凭据、数据库和备份副本都不属于公开展示材料。

管理服务限制本机监听、使用强凭据与双因素认证、控制网络访问范围等，是文档中的配置与验收要求；不能仅凭文档列出了这些步骤，就认定所有加固项均已验证完成。

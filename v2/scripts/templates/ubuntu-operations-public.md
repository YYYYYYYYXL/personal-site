# Ubuntu 服务器运维

> 本文根据原维护手册提炼为通用运维笔记，不描述个人服务器的真实部署。文中的域名、服务名和目录均为教学示例。

## 公共基础设施与应用边界

在一台 Ubuntu 服务器上，多项应用可能共用 Nginx、Docker、Certbot、systemd 和 SSH。维护某个应用时，应先区分应用资源与共享资源，避免影响其他服务。

| 层次 | 作用 | 维护时关注什么 |
| --- | --- | --- |
| Ubuntu | 操作系统、文件与权限 | 磁盘空间、系统日志、用户权限 |
| Nginx | Web 入口和反向代理 | 配置语法、上游连通性、访问日志 |
| Certbot | HTTPS 证书签发与续期 | 证书有效期、续期任务 |
| Docker Compose | 定义和管理应用容器 | 服务状态、镜像版本、数据卷 |
| systemd | 管理系统服务 | 启动状态、服务依赖、日志 |
| SSH | 远程管理 | 公钥认证、访问权限、服务配置 |

## 容器化 Web 应用

容器化应用需要分清镜像、容器、网络和数据卷。删除容器并不意味着持久化数据已被清除，删除数据卷则可能导致数据无法恢复。

维护时先检查应用使用的 Compose 配置，再查看服务状态和日志：

```bash
docker compose ps
docker compose logs --tail 100
```

这些命令应在目标应用的 Compose 目录中执行。更新前记录镜像版本，并备份数据库、数据卷或其他需要保留的内容。

## 静态网站

静态网站通常由 Nginx 直接读取构建产物，不需要额外的运行期应用进程。源码、构建产物和服务器发布目录应分开管理。

```text
源码与内容
    ↓ 本地或 CI 构建
静态产物
    ↓ 发布前备份
站点目录
    ↓ Nginx
浏览器
```

更新静态文件与修改 Nginx 配置是不同的操作。配置修改后，先运行语法检查，确认无误再考虑重载：

```bash
sudo nginx -t
```

## 3X-UI 与 Xray 的通用维护边界

3X-UI 管理面板与 Xray 数据处理进程承担不同职责。理解概念时，应区分管理平面与数据平面；本公开笔记不提供实际节点拓扑、软件版本、监听端口、Reality 目标、SNI 或订阅配置。

### 可以记录的通用内容

- 服务如何由 systemd 管理。
- 如何查看运行状态与日志。
- 升级前应备份哪些类型的数据。
- 反向代理、证书与应用服务各自负责什么。

### 不进入公开笔记的内容

- 面板账号密码和访问入口。
- 节点标识、认证材料、Reality 私钥与 Short ID。
- 订阅地址、完整分享链接及数据库副本。
- 实际软件版本、网络拓扑、对外端口和目标站点。

查看服务状态和近期日志的一般形式如下，执行时将示例名替换为实际服务名：

```bash
systemctl status example-app.service
journalctl -u example-app.service -n 100 --no-pager
```

日志也可能包含个人或认证信息，分享日志前应再次检查。

## 日常检查顺序

1. 先确认应用是否运行，再检查端口和上游连接。
2. 查看应用日志及 systemd 日志，记录实际报错。
3. 检查 Nginx 配置、证书有效期与续期任务。
4. 确认防火墙规则与应用用途一致，避免意外暴露管理服务。
5. 检查磁盘空间以及备份是否可用。

```bash
df -h
systemctl --failed
sudo certbot certificates
systemctl status certbot.timer
```

## 备份与恢复

备份的关键是能够恢复，而不仅是存在一个副本。应明确需要保留的应用配置、数据库、数据卷和静态文件，记录备份位置、时间及恢复步骤。

备份文件可能包含认证材料，应限制访问权限，也不应作为网站附件或 Git 仓库内容发布。

## 项目下线与资源清理

原手册包含针对具体服务器的完整删除命令。公开版保留下线流程，不提供可直接复制的批量删除指令：

1. 确认目标应用与其他服务的依赖关系。
2. 备份必要数据，并明确是否需要回滚。
3. 停止目标服务，确认其进程和监听已退出。
4. 按资产清单清理该应用专属的配置、容器与数据。
5. 对专属 DNS、证书、域名及防火墙规则逐项核对。
6. 确认其他应用与共享基础设施仍能正常工作。

共享的 Nginx、Docker、Certbot、SSH 和公共 Web 入口，不应随单个应用一起删除。
